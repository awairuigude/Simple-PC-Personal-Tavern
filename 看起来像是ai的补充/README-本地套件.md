# Simple PC Personal Tavern 本地套件

这是一个放在 F 盘、只供本机使用的 SillyTavern + KoboldCpp 套件。SillyTavern 负责角色卡、Persona、世界书、聊天记录、导入和记忆；KoboldCpp 负责加载 GGUF 模型并提供本地 API。

默认服务只监听 `127.0.0.1`：

- 酒馆界面：`http://127.0.0.1:8000`
- 本地模型 API：`http://127.0.0.1:5001`
- 模型接口：Text Completion / KoboldCpp
- 当前本地用户：`用户`

截至 2026-08-12，本套件已在本机完成启动验证：模型 API 在 5001 端口正常返回，酒馆在 8000 端口返回 200，酒馆界面已成功连接到 KoboldCpp 模型。当前运行的是中文主模型；如不需要使用，关闭模型窗口即可释放显存。

## 目录

```text
app/       独立的 Simple-PC-Personal-Tavern 副本和 node_modules
models/    GGUF 模型文件
runtime/   KoboldCpp、aria2 和浏览器测试运行包
presets/   系统提示词、叙事模块、TXT 示例和评测用例
tests/     固定测试材料
logs/      手动启动时可保存日志的位置
```

这个副本与桌面上的其他 SillyTavern 工作树相互独立。不要把 `app/data` 与其他安装共用，否则角色卡、聊天和设置可能混在一起。

## 已安装模型

### 中文主模型

文件：`models/qwen2.5-14b-roleplay-zh-q4_k_m.gguf`

- Qwen2.5 14B Instruct 的中文角色扮演微调
- Q4_K_M，文件大小 `8988108736` 字节
- SHA-256：`1d6e2fae10eb4779950518a8c9b81c66167552d54d582ba3dcd35d4fa1a5d327`
- 原生上下文元数据：32768；本机启动上下文：12288
- ChatML 模板已写入 GGUF 元数据，和本套件的 ChatML 预设匹配

它的中文措辞和角色风格是当前主候选，但实测有明显的短停笔倾向：相同场景在直接 API 测试中通常约生成 14 到 58 token 后自然结束，即使请求上限提高到 500 到 700 token 也可能提前结束。这不是下载损坏，也不是 `max_tokens` 没生效；是该微调权重的生成习惯。提高酒馆生成量只能提高上限，不能保证模型一定写满。

### Qwen3 对照模型

文件：`models/Qwen3-14B-abliterated-Q4_K_M.gguf`

- `mlabonne/Qwen3-14B-abliterated` 的 GGUF 量化版
- Q4_K_M，发布文件约 9.00 GB
- Apache-2.0
- 用于比较指令接受度、拒答倾向和长回复能力

该模型是实验性低拒答权重，不应仅凭“abliterated”标签判断质量。文件 SHA-256 已校验：`3fe972a7c6e847ec791453b89a7333d369fbde329cbd4cc9a4f0598854db5d54`。需要比较时先停止中文模型，再用 `02-启动低拒答对照模型.cmd` 启动。

## 启动方式

最简单的方式是双击：

1. `01-启动中文角色扮演模型.cmd`
2. 等待模型 API 在 5001 端口就绪
3. `03-启动酒馆.cmd`

也可以双击 `04-启动全套-中文模型.cmd`，它会先启动中文主模型，检测 5001 端口，然后启动酒馆。

停止服务可运行 `05-停止本地模型.cmd`。当前启动参数如下：

```text
--usecuda 0
--autofit
--autofitpadding 1200
--contextsize 12288
--quantkv q8_0
--threads 12
--blasthreads 12
--batchsize 512
--jinja
--jinjathink false
--defaultgenamt 2048
--host 127.0.0.1
--port 5001
```

停止脚本只匹配本套件目录下启动的 KoboldCpp，不会按进程名结束电脑上的其他 KoboldCpp 实例。

`--defaultgenamt 2048` 是 KoboldCpp 的默认值；酒馆每轮还会发送自己的生成量。本套件的酒馆用户设置已经把生成量设为 1200 token，实际输出仍可能因 EOS、停止串、角色卡或模型自身的停笔习惯而提前结束。

## 已实测资源占用

设备：RTX 4060 Laptop 8 GB、24 GB 内存、i7-13650HX。

中文主模型在 12K 上下文、KV Q8、自动分层下：

- API 就绪时间：约 42 秒
- GPU 显存：约 6887 / 8188 MB
- KoboldCpp 后端工作集：约 4.6 GiB
- 启动后系统可用内存：约 9.9 GiB
- 提示词处理：约 210 到 264 token/s
- 生成速度：约 9.2 token/s
- API：`/api/v1/model`、`/v1/models`、`/v1/chat/completions` 均实测可用

Qwen3 对照模型在同一台机器、同样 12K 配置下：

- GPU 显存：约 6960 / 8188 MB
- 生成速度：约 8.36 token/s
- 长场景测试：请求 650 token，实际生成 479 token，约 653 个汉字，未因短 EOS 立即结束
- 明确成年亲密叙事测试：未拒答、未突然淡出
- 反派不洗白测试：未强制道德说教或悔悟
- 用户自主权测试：不合格，仍会替用户角色写动作和让用户角色开口
- 中文质量：可用但重复感和主语混乱比中文主模型更明显

因此当前默认仍是中文主模型；Qwen3 更适合在需要更长回复或比较拒答倾向时手动切换，不是全面替代。

12K 是当前稳定档。可以继续试 16K，但需要重新观察显存、系统内存和生成速度；不要把 GGUF 文件的原生 32K 元数据等同于这台 8 GB 显卡在 32K 下的舒适运行档。

## 酒馆连接设置

本套件的独立用户设置已经写入：

```text
API：文本补全
API 类型：KoboldCpp
API 地址：http://127.0.0.1:5001
上下文：12288
生成量：1200
Context：私人创作-ChatML
Instruct：私人创作-ChatML
采样：私人创作-稳定正文
```

这些是全局生成设置，不会显示在“新建角色”编辑页中。顶部滑杆图标“AI 响应配置”里可看到生成量、上下文和文本补全采样预设；顶部 `A` 图标“高级格式化”里可看到 Context Template 和 Instruct Mode。12K 上下文需要保持“解锁”开启，否则界面会把数值压回 8192。

如果界面显示未连接：

1. 打开酒馆左上角的“API 连接”。
2. API 选择“文本补全”。
3. API 类型选择“KoboldCpp”。
4. 地址填写 `http://127.0.0.1:5001`。
5. 点击“连接”，看到 `koboldcpp/qwen2.5-14b-roleplay-zh-q4_k_m` 即成功。

酒馆的 KoboldCpp 地址字段是 `server_urls.koboldcpp`，不是旧版本教程里常见的 `api_server` 字段。

## 角色卡、人设和背景

酒馆原生支持：

- PNG/JSON/CharX 角色卡
- Persona 用户人设
- Scenario 场景
- World Info 世界书
- 示例对话和风格锚点
- 独立聊天记录、分支和消息编辑

角色文件导入支持 `PNG`、`JSON`、`YAML/YML`、`CharX` 和 `BYAF`。角色列表顶部的“文件导入”按钮用于导入这些角色卡；普通 TXT 总结不是角色卡文件。

新建角色时，建议这样分配内容：

```text
角色描述：角色身份、外貌、性格、关系、经历、知识范围和说话习惯
开场白：故事当前节点的第一条角色消息，直接按目标文风书写
情景/场景：时间、地点、故事背景、当前关系、剧情总结、状态和未结事件
示例对话：几段最能代表角色语气和叙事风格的用户/角色对话
创作者注释：只供人阅读，不会稳定发送给模型，不要把关键设定只放这里
Persona：用户所扮演人物的身份、外貌、经历、目标和称呼
```

推荐把内容分层：

```text
角色卡：身份、性格、说话方式、关系和边界
Persona：用户角色的身份、经历、外观和长期目标
Scenario：当前故事起点和地点
World Info：只在关键词出现时插入的世界设定
剧情总结：累计主线、关系变化、秘密、物品和未结事件
阶段总结：最近一段剧情的具体状态
状态账本：时间、地点、人物位置、衣着、身体状态和物品归属
风格锚点：从旧聊天中挑选 3 到 8 段最能代表文风的原文
最近原文：当前节点附近的若干轮对话
```

不要只给模型一份概括性总结就要求它完全复原旧文风。总结负责压缩事实，风格锚点和最近原文负责恢复措辞、节奏、称呼和动作密度。上下文有限时，优先保留当前节点、最近原文、未结事件和相关早期片段。

## TXT 导入

文件：`presets/04-TXT导入格式示例.txt`

准确入口：先保存或导入角色并进入该角色的聊天；点击消息输入框左侧的三横线“聊天选项”，选择“管理聊天文件”，再点击弹窗顶部的“导入聊天”。聊天导入支持 `TXT`、`JSON` 和 `JSONL`。角色编辑页里的“更多...”菜单不包含聊天导入。

导入器支持英文冒号和中文冒号，也支持这些总结标签：

```text
剧情总结：
新通用总结：
通用总结：
阶段总结：
本轮总结：
历史总结：
前情提要：
```

对话建议写成：

```text
剧情总结：
两名成年角色在旧城调查账本，账本去向未明，双方仍互相试探。

阶段总结：
当前时间是雨夜，地点是车站，用户手里有旧钥匙。

用户：我把钥匙放到桌上，没有解释。

角色：她看着钥匙，手指停在半空，没有立即拿起。

新通用总结：
长期保留：旧钥匙、账本、双方互相试探；当前未结是她是否承认认识这把钥匙。
```

导入行为：

- 原始 TXT 会被转换为 SillyTavern JSONL 聊天记录并保存。
- 已识别的总结会挂到对应消息的 `txt_import` 和 `qvink_memory` 元数据。
- 原文不会因为文件是 1 MB 就在导入时截断。
- 本地解析测试使用约 906 KB、7000 条消息和 7000 个总结块，完整保留了字节数、消息数量、角色顺序和记忆元数据。
- 导入完整原文不等于每轮都把完整原文发送给模型。模型每轮仍受 12288 token 上下文限制，酒馆会按上下文预算裁剪历史。

对于 1.08 MB 左右的旧对话，推荐导入原文后再准备：累计总结、最近阶段总结、状态账本、3 到 8 段风格锚点，以及当前节点前后的原文。这样切换模型时也能保留同一条剧情。

## 创作提示词模块

文件：`presets/01-成人虚构-系统提示词.txt`、`presets/02-叙事模块.md`、`presets/03-风格锚点模板.md`。

模块包括：

- 用户自主权：不替用户写新的台词、行动、感受和关键决定
- 防抢话：轮到用户回应时停住
- 防全知：角色只能使用自己知道的信息
- 防绝望：不无依据地把冲突升级为不可逆绝境
- 防强制升华：不在结尾自动加入人生感悟或救赎
- 防强制惩罚：不因道德判断自动安排报应或洗白
- 慢节奏：一轮聚焦一个连续场景
- 长回复：给出目标篇幅，但允许模型在自然节点停下
- 导演指令：把括号中的后续剧情作为编剧层要求，从当前节点演绎

“开放”主要由三层共同决定：模型权重、采样参数、角色卡/系统提示词。提示词可以减少说教和跳出故事，但不能把一个本身倾向短答或拒答的模型变成另一种权重；本地模型也不会自动继承云端 DeepSeek 的模型能力。

## 总结模型和记忆

酒馆的总结扩展可以使用当前已连接模型，也可以以后单独接一个便宜、快速的总结模型。长篇创作建议把正文模型和总结模型分开考虑：

- 正文模型：优先中文风格、人物一致性和场景推进
- 总结模型：优先事实抽取、状态账本和稳定格式
- 总结间隔：先按 8 到 12 轮观察，再按实际上下文增长调整
- 总结长度：不要只固定一个很小的 4000 上限；应按主线数量和未结事件增加

如果总结越来越长，优先拆成“累计总账 + 阶段总结 + 状态账本”，不要把所有旧总结无止境拼接成一段。

## 安全边界和网络范围

这是本地虚构创作套件，不包含云端 API 代理、API Key 提取或第三方审核绕过脚本。使用本地 GGUF 的意义是模型和提示词在本机处理，控制路径更直接；它不等于模型会服从所有内容，也不等于任何输入都适合生成。所有亲密创作角色应在卡片和设定中明确为成年人。

不要把 `127.0.0.1` 改成 `0.0.0.0`，除非你明确知道自己要让局域网设备访问，并且已经配置身份验证和防火墙。手机通过飞书给电脑下指令属于另外一层自动化：可以通过本地 webhook、飞书机器人和受限脚本实现，但当前套件没有开启远程控制。
