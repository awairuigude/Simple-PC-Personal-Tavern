# 使用指南

这份指南只描述当前仓库已经能够完成的操作。Qvink Memory、Tavern Helper、MVU/状态栏等第三方扩展需要在本机另行安装和配置，不会从公开 Git 仓库自动恢复。

## 1. 安装与启动

安装 Node.js 20 或更高版本，然后在 PowerShell 中执行：

```powershell
git clone https://github.com/awairuigude/Simple-PC-Personal-Tavern.git
cd Simple-PC-Personal-Tavern
npm install
npm start
```

浏览器打开 <http://127.0.0.1:8000>。如果端口被占用，可在首次生成的 `config.yaml` 中修改 `port`。该文件包含本机设置并被 Git 忽略。

默认保持 `listen: false`，这样服务只允许本机访问。不要直接把端口映射到公网。

## 2. 连接模型

在顶部 API 连接面板选择服务类型，填写 API 地址、Key 和模型名。可使用：

- 官方云 API
- OpenAI 兼容中转
- SillyTavern 已支持的 Claude、Gemini 等连接
- 本地 OpenAI 兼容推理服务

不同来源的模型名不一定相同。中转站显示的名称可能是别名，应以该服务实际文档和账单为准。API Key 只填在本机连接设置中，不要写进角色卡、聊天、README 或提交到 Git。

切换模型不会删除当前聊天，但新模型是否能延续语气取决于它收到的角色资料、记忆、近期原文和上下文限制。

## 3. 准备角色资料

至少准备：

1. 一张角色卡，描述 AI 扮演者。
2. 一个 Persona，描述用户在故事中的身份。
3. 必要时创建世界书，存放地点、组织、配角和规则。
4. 用 First Message 和 Example Messages 定下文风。

详细字段见 [人设与背景模板.md](人设与背景模板.md)。

## 4. 整理要导入的 TXT

最稳定的格式是一条消息一个明确标签：

```text
用户：第一条用户消息，可以换行。
仍然属于用户消息。

林遥：第一条角色回复。

剧情总结：最近一个阶段发生的事实。

用户：继续。
林遥：后续回复。

新通用总结：截至这里为止需要长期保留的累计事实。
```

建议：

- 把 AI 的标签直接写成目标角色名，减少 `AI` 到角色名的歧义。
- 阶段总结使用 `剧情总结`，累计覆盖性总结使用 `新通用总结` 或 `前情提要`。
- 总结只写已经发生的事实，不要把 `（后续剧情：...）` 一类导演指令记成已发生。
- 保留动作归属、人物关系、时间地点、物品去向、身体状态和未解决事件。
- 不必为了导入把 1 MB 文件拆开，但第一次应先截取一小份测试格式。

## 5. 导入 TXT

1. 打开目标角色。
2. 打开“聊天记录”管理窗口。
3. 点击“导入聊天”。
4. 选择 `.txt` 文件。
5. 导入完成后打开新生成的聊天。
6. 检查前几条和最后几条消息的说话人归属。
7. 搜索几个关键场景，确认原文没有丢失。

导入不会请求模型，也不会覆盖原 TXT。SillyTavern 会把转换后的结果保存为本机 JSONL 聊天。

## 6. 导入器如何处理总结

- `剧情总结` 等阶段总结附着到前一条聊天消息。
- 最后一份 `新通用总结`、`通用总结`、`前情提要` 等累计总结成为长期基线。
- 基线之前的旧总结仍保留，但标记为不再重复注入。
- 基线之后的阶段总结作为新增进展。
- 总结块不显示为普通角色台词。

如果安装了兼容的 Qvink Memory，扩展可以读取这些元数据。没有安装时，原始聊天仍然可用，只是模型不会自动收到这些总结。

## 7. 长篇续写的建议上下文

1 MB 历史不能每轮原样发送给模型。实用的续写输入应包含：

- 角色卡、Persona 和当前相关世界书
- 一份可靠的累计总结
- 最近几份阶段总结
- 当前状态账本
- 最近 20-40 轮原文
- 与当前场景相关的若干早期原文
- 少量代表文风的示例

当前仓库只完成历史迁移和总结元数据种入。相关旧事检索、可配置近期窗口和状态账本统一注入仍属于后续开发。

## 8. 回复长度排查

设置 4,000 token 最大输出但只得到约 2,000，不代表剩余额度“被吃掉”。依次检查：

1. 回复是否自然结束，有没有完整收束句。
2. 预设或角色卡是否要求简短回答。
3. 是否配置停止字符串。
4. 接口返回的 `finish_reason` 是 `stop`、`length`、`content_filter` 还是其他值。
5. 上游中转是否有自己的输出上限、超时和重试。
6. 输入上下文是否已接近模型总窗口。
7. 同一个提示在不同尺度内容下是否稳定复现。

仅凭长度无法断言是审核。要判断原因，应保存浏览器网络响应或服务端日志中的状态码、`finish_reason` 和 usage。

## 9. 备份

Git 仓库不等于聊天备份。升级或改代码前，单独备份本机 `data` 目录，以及用到的第三方扩展配置。不要把含私人聊天和 API Key 的备份推到公开 GitHub。
